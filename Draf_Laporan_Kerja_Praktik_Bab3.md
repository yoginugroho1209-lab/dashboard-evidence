### 3.1 Pengembangan Antarmuka Web (Frontend)

#### 3.1.1 HTML dan CSS

*HyperText Markup Language* (HTML) merupakan bahasa markah standar (markup language) yang digunakan untuk menyusun kerangka dan struktur dasar dari sebuah dokumen atau halaman web. HTML beroperasi dengan menggunakan sekumpulan elemen berupa *tag* yang memberikan instruksi kepada peramban web (*web browser*) mengenai bagaimana teks, gambar, tautan, dan elemen antarmuka lainnya harus dikelompokkan dan ditampilkan secara terstruktur [1]. Pada pengembangan *Dashboard Evidence*, HTML berfungsi sebagai fondasi utama penyusun elemen antarmuka (skeleton) yang merepresentasikan data visual, formulir unggahan, dan tabel laporan operasional.

Untuk melengkapi struktur dasar tersebut, diperlukan *Cascading Style Sheets* (CSS) guna mengelola tata letak dan aspek estetika. CSS adalah bahasa pemrograman desain (*style sheet language*) yang digunakan untuk mengatur tampilan visual dari elemen-elemen HTML, meliputi pengaturan pewarnaan, tipografi (jenis huruf), tata letak posisi ruang (*margin* dan *padding*), hingga implementasi animasi [2]. Penggunaan CSS memungkinkan pengembang untuk memisahkan antara struktur konten utama (HTML) dengan presentasi visualisasinya. Pemisahan arsitektur antarmuka ini dinilai sangat penting dalam rekayasa perangkat lunak berbasis web, karena dapat meningkatkan efisiensi pemeliharaan kode (*maintainability*) serta mempermudah penerapan desain responsif (*responsive web design*) yang mampu beradaptasi dengan berbagai dimensi ukuran layar perangkat [3]. Kolaborasi yang baik antara HTML dan CSS merupakan fondasi krusial agar visualisasi data infrastruktur jaringan yang kompleks pada sistem dapat disajikan secara intuitif, rapi, dan interaktif bagi *validator* lapangan.

#### 3.1.2 JavaScript

*JavaScript* merupakan bahasa pemrograman tingkat tinggi yang dinamis dan berorientasi objek yang menjadi salah satu dari tiga pilar utama dalam pengembangan *World Wide Web* (WWW), bersanding dengan HTML dan CSS. Jika HTML berfungsi sebagai kerangka dasar dan CSS sebagai pembentuk visualisasi antarmuka, maka JavaScript memegang peran krusial dalam menyematkan logika serta interaktivitas ke dalam sebuah halaman web [1]. Bahasa pemrograman ini memungkinkan halaman web yang awalnya bersifat statis menjadi dinamis, sehingga sistem mampu merespons berbagai tindakan (seperti *klik* atau *unggah file*) dari pengguna secara langsung tanpa keharusan untuk memuat ulang (*reload*) keseluruhan halaman secara terus-menerus [2].

Seiring dengan perkembangan standarisasi *ECMAScript* modern, JavaScript kini dilengkapi dengan kapabilitas asinkron (*asynchronous programming*) yang sangat mumpuni. Pada perancangan aplikasi *Dashboard Evidence* ini, JavaScript digunakan secara ekstensif di sisi klien (*client-side*) sebagai motor penggerak utama logika sistem. Implementasinya mencakup proses manipulasi *Document Object Model* (DOM), pembacaan berkas citra (*file reader*) saat pengguna mengunggah foto lapangan, pemrosesan ekstraksi metadata EXIF, hingga pengaturan konektivitas asinkron berbasis *Fetch API* untuk berkomunikasi dengan model kecerdasan buatan dan *backend* basis data [3]. Berkat ekosistem fungsionalitas JavaScript tersebut, pengolahan serta verifikasi data infrastruktur dapat dieksekusi secara instan dan *real-time* oleh antarmuka sistem.

#### 3.1.3 React.js

*React.js* adalah sebuah pustaka (*library*) *open-source* berbasis JavaScript yang dikembangkan dan didukung penuh oleh perusahaan teknologi Meta (sebelumnya Facebook). Pustaka ini dirancang secara khusus dengan paradigma deklaratif untuk memfasilitasi pembangunan antarmuka pengguna (*User Interface*) yang kompleks, efisien, dan interaktif, khususnya pada pengembangan Aplikasi Halaman Tunggal (*Single Page Application* / SPA) [1]. Fondasi utama dari React.js terletak pada pendekatan arsitektur berbasis komponen (*component-based architecture*), di mana sebuah antarmuka yang besar dipecah menjadi modul-modul atau komponen-komponen kecil yang berdiri sendiri (*encapsulated*) dan dapat digunakan berulang kali (*reusable*) di berbagai bagian sistem.

Keunggulan komputasional paling revolusioner dari React.js adalah implementasi mekanisme *Virtual Document Object Model* (Virtual DOM). Pada pendekatan pemrograman web konvensional, setiap perubahan data akan langsung memanipulasi struktur DOM asli pada peramban, yang membutuhkan beban komputasi tinggi. Sebaliknya, saat terjadi pembaruan data, React.js akan memodifikasi struktur *Virtual DOM* terlebih dahulu di dalam memori, lalu melakukan komparasi (*diffing algorithm*) untuk menemukan elemen spesifik mana saja yang berubah [2]. Setelah itu, sistem hanya akan merender ulang dan menyinkronkan komponen yang terdampak perubahan tersebut ke DOM asli [3]. Pada perancangan aplikasi *Dashboard Evidence*, kemampuan manajemen *state* (status data) dan efisiensi render ini sangat diandalkan untuk menangani proses interaktif, seperti sinkronisasi pemuatan deteksi objek YOLOv8, penarikan data koordinat EXIF, hingga memuat lapisan peta KML yang padat data tanpa mengurangi performa (*lag*) antarmuka sistem.

### 3.2 Backend dan Deployment

#### 3.2.1 Backend as a Service (BaaS) Supabase

*Backend as a Service* (BaaS) merupakan salah satu model arsitektur komputasi awan (*cloud computing*) yang menyediakan infrastruktur peladen (*server*) dan logika *backend* siap pakai bagi pengembang perangkat lunak. Melalui pendekatan BaaS, pengembang tidak perlu lagi membangun, mengonfigurasi, dan memelihara infrastruktur *server* fisik maupun basis data dari awal (*from scratch*). Sebagai gantinya, pengembang dapat langsung mengintegrasikan berbagai kapabilitas sistem (*seperti manajemen data, penyimpanan, dan autentikasi*) ke dalam aplikasi sisi klien menggunakan layanan *Application Programming Interface* (API) dan *Software Development Kit* (SDK) yang telah disediakan [1].

Dalam perancangan aplikasi *Dashboard Evidence* ini, manajemen infrastruktur data sepenuhnya didelegasikan pada *Supabase*. Supabase adalah sebuah *platform* BaaS berbasis sumber terbuka (*open-source*) yang dirancang secara fundamental di atas sistem manajemen basis data relasional (*Relational Database Management System*) *PostgreSQL* tingkat industri [2]. Dikenal sebagai alternatif tangguh di ranah sumber terbuka, Supabase menyediakan ekosistem terpadu yang dimanfaatkan ke dalam tiga fungsi krusial pada sistem ini. Pertama, **Supabase Database (PostgreSQL)** digunakan untuk menyimpan dan merelasikan data tekstual terstruktur, seperti histori validasi deteksi objek, rute KML proyek, serta log titik koordinat spasial. Kedua, **Supabase Storage** difungsikan sebagai sistem penyimpanan awan (*cloud bucket*) untuk menampung seluruh berkas citra (*file* foto) *evidence* lapangan yang berukuran besar. Ketiga, **Supabase Authentication** diterapkan untuk mengamankan dan mengelola sesi kontrol akses masuk (*login*) bagi para validator operasional [3]. Dengan mengimplementasikan Supabase, sinkronisasi aliran data antara antarmuka React.js dan basis data dapat dieksekusi secara cepat, instan, dan *real-time* dengan meminimalisir kompleksitas konfigurasi peladen konvensional.

#### 3.2.2 Vercel Cloud Hosting

*Deployment* (perilisan atau penyebaran) merupakan fase operasional penting dalam siklus hidup rekayasa perangkat lunak, di mana kode sumber yang dikembangkan di lingkungan lokal (komputer pengembang) ditransformasikan menjadi aplikasi langsung (*live*) yang dapat diakses oleh pengguna akhir melalui jaringan internet. Untuk memfasilitasi proses perilisan *Dashboard Evidence*, sistem ini mengadopsi layanan arsitektur awan dari *Vercel*. Vercel adalah *platform cloud hosting* komputasi modern yang dioptimalkan secara khusus untuk menyebarkan kerangka kerja antarmuka (*frontend frameworks*), situs web statis, serta mengeksekusi fungsi nirkaden (*Serverless Functions*) dengan kinerja tinggi [1].

Keunggulan utama yang mendasari penggunaan Vercel adalah kemampuan otomatisasi alur kerja *Continuous Integration and Continuous Deployment* (CI/CD) melalui integrasi bawaannya (*native integration*) dengan platform sistem kontrol versi (*Version Control System*), seperti GitHub. Setiap kali pengembang melakukan pembaharuan kode sumber (*push commit*) ke repositori GitHub, mesin Vercel akan secara otomatis mendeteksi perubahan tersebut, mengeksekusi proses kompilasi (*build*), dan merilis versi terbaru aplikasi tanpa campur tangan manual [2]. Lebih jauh lagi, Vercel mendistribusikan antarmuka aplikasi melalui arsitektur *Global Edge Network* atau semacam *Content Delivery Network* (CDN). Arsitektur ini memastikan bahwa aset-aset *website* direplikasi dan diletakkan pada titik *server* terdekat dengan lokasi pengguna, sehingga waktu pemuatan halaman (*page load time*) menjadi sangat singkat dan tingkat ketersediaannya (*availability*) tetap stabil [3]. Dengan mengimplementasikan layanan Vercel, *Dashboard Evidence* dapat langsung diakses kapan pun oleh validator lapangan melalui peramban (*browser*) secara andal, tanpa membebani perusahaan dengan biaya pemeliharaan *server* fisik yang rumit.

### 3.3 Kecerdasan Buatan dan Pemrosesan Citra

#### 3.3.1 Object Detection

*Object Detection* (Deteksi Objek) merupakan salah satu sub-bidang inti dari visi komputer (*Computer Vision*) dan kecerdasan buatan (*Artificial Intelligence*) yang berfokus pada analisis dan pemahaman semantik visual dari sebuah data gambar digital maupun video. Secara fungsional, teknologi ini memiliki perbedaan mendasar dengan klasifikasi citra (*Image Classification*). Jika klasifikasi citra hanya bertujuan untuk memprediksi *apa* kategori utama dari sebuah gambar secara keseluruhan, maka deteksi objek melangkah lebih jauh dengan kemampuan lokalisasi; yaitu mengenali *apa* saja objek yang ada di dalam gambar tersebut, sekaligus menentukan *di mana* lokasi persis koordinat piksel spasialnya melalui penggambaran kotak pembatas (*bounding box*) berserta nilai tingkat kepercayaan prediksinya (*confidence score*) [1].

Secara konseptual, model komputasi deteksi objek modern bekerja dengan memanfaatkan arsitektur jaringan saraf tiruan dalam (*Deep Neural Networks*), khususnya turunan dari *Convolutional Neural Networks* (CNN), guna mengekstrak fitur-fitur kompleks dari sebuah citra mentah dan mempelajari representasi polanya secara matematis [2]. Dalam ruang lingkup operasional pembangunan infrastruktur telekomunikasi, penerapan teknologi deteksi objek menawarkan solusi transformatif. Secara historis, proses validasi bukti lapangan (*evidence*) mengharuskan administrator untuk melakukan inspeksi visual ratusan foto satu per satu secara manual guna memastikan ketiadaan manipulasi pelaporan dan eksistensi fisik perangkat, seperti tiang utilitas. Proses konvensional ini sangat menyita waktu dan rentan terhadap kelalaian manusia (*human error*). Melalui integrasi algoritma *object detection* ke dalam sistem, proses kurasi visual tersebut sepenuhnya diotomatisasi. Sistem mampu memindai dan memverifikasi keberadaan aset tiang di dalam foto secara instan, transparan, dan sangat akurat, yang pada akhirnya mendongkrak efisiensi proses audit aset perusahaan secara signifikan [3].

#### 3.3.2 YOLOv8 (You Only Look Once)

Algoritma *You Only Look Once* (YOLO) merupakan salah satu terobosan arsitektur jaringan saraf tiruan yang paling berpengaruh dalam ranah pendeteksian objek seketika (*real-time object detection*). Sebelum kemunculan YOLO, sistem deteksi objek konvensional (seperti R-CNN) menggunakan pendekatan komputasi multi-tahap yang mengandalkan ekstraksi proposal wilayah gambar, sehingga memakan waktu inferensi yang sangat lambat. Sebaliknya, YOLO secara fundamental merumuskan tugas pendeteksian sebagai permasalahan regresi spasial tunggal. Sistem ini memproses keseluruhan gambar hanya dalam satu kali eksekusi (*single forward pass*) melintasi jaringan saraf untuk secara simultan memprediksi koordinat spasial kotak pembatas (*bounding boxes*) dan probabilitas kelas objek [1]. Mekanisme satu tahap (*one-stage detector*) ini menghasilkan kecepatan pemrosesan yang sangat tinggi tanpa mengorbankan metrik akurasi secara drastis [2].

*YOLOv8* adalah generasi pembaruan terkini (versi kedelapan) dari lini keluarga algoritma YOLO yang dikembangkan dan dikelola oleh Ultralytics. Iterasi terbaru ini memperkenalkan berbagai pembaruan arsitektural tingkat lanjut, meliputi penggunaan arsitektur tanpa jangkar (*anchor-free detection head*), optimalisasi fungsi kerugian (*loss functions*), dan penguatan struktur jaringan ekstraksi fitur (*backbone network*). Inovasi matematis tersebut menjadikan YOLOv8 memiliki tingkat presisi (mAP - *mean Average Precision*) yang jauh lebih tajam, lebih ringan, dan sangat fleksibel dibandingkan generasi-generasi pendahulunya [3]. 

Pada perancangan *Dashboard Evidence*, pemilihan YOLOv8 didasarkan pada kebutuhan sistem akan keseimbangan optimal antara akurasi tinggi dan latensi rendah. Algoritma ini dilatih secara spesifik (*custom training*) untuk mengenali struktur fisik tiang jaringan telekomunikasi dengan berbagai tingkat variasi pencahayaan, jarak, dan sudut pandang lapangan. Dengan efisiensi komputasi YOLOv8, sistem web mampu memvalidasi keabsahan objek di dalam foto *evidence* hanya dalam kurun waktu sepersekian detik, sehingga proses pelaporan tidak membebani kinerja sistem dan terhindar dari waktu tunggu komputasi yang panjang (*bottleneck*).

#### 3.3.3 Roboflow

*Roboflow* adalah sebuah *platform* komputasi visi (*computer vision platform*) terpadu (*end-to-end*) yang dirancang khusus untuk menyederhanakan dan mengotomatisasi siklus hidup pengembangan model kecerdasan buatan, mulai dari kurasi dataset hingga fase pelatihan jaringan. Dalam ranah rekayasa model *custom object detection*, kualitas, kuantitas, serta struktur dataset memegang peranan yang sangat deterministik terhadap tingkat akurasi akhir yang dihasilkan oleh model prediktif [1]. Platform Roboflow menyediakan instrumen fungsional bagi pengembang untuk melakukan manajemen citra secara komprehensif, yang mencakup proses pelabelan objek (*annotation*), prapemrosesan ukuran resolusi (*preprocessing*), hingga augmentasi data (*data augmentation*).

Teknik augmentasi data merupakan metode rekayasa citra untuk melipatgandakan variansi sampel gambar secara artifisial—seperti memanipulasi tingkat kontras pencahayaan, merotasi sudut gambar, hingga menyisipkan gangguan ketajaman (*noise*). Tujuannya adalah untuk mencegah model mengalami kelebihan kecocokan (*overfitting*) saat tahap pelatihan, sekaligus mendongkrak ketahanan algoritma saat dihadapkan pada ketidakpastian kondisi visual di lapangan [2]. Pada tahap perancangan model untuk *Dashboard Evidence*, Roboflow dimanfaatkan secara vital sebagai sistem manajemen dataset tiang telekomunikasi. Ratusan sampel foto *evidence* mentah diunggah ke *platform* ini untuk dilakukan anotasi *bounding box* secara presisi. Setelah melalui proses augmentasi, Roboflow mengompilasi dan mengekspor seluruh struktur berkas citra berserta teks koordinat labelnya (format `.txt` dan `.yaml`) yang memiliki kompatibilitas absolut dengan arsitektur standar *Ultralytics YOLOv8* [3]. Melalui pemanfaatan Roboflow, fase preparasi dataset yang secara tradisional memakan waktu berhari-hari dapat diselesaikan dengan struktur yang optimal dan bebas dari anomali format data.

### 3.4 Geospasial dan Validasi Lokasi

#### 3.4.1 Metadata EXIF (Exchangeable Image File Format)

*Exchangeable Image File Format* (EXIF) merupakan sebuah standar format industri spesifikasi struktural yang digunakan untuk menanamkan (*embed*) data informasi atribut tambahan (metadata) ke dalam berkas media citra digital, khususnya pada ekstensi file seperti JPEG dan TIFF. Standarisasi struktur ini diadopsi secara luas dan diimplementasikan secara otomatis oleh perangkat perekam citra modern saat ini, mulai dari kamera digital konvensional hingga telepon pintar (*smartphone*) [1]. Rangkaian data yang direkam di dalam struktur metadata EXIF mencakup parameter teknis ekstensif pada saat perangkat menangkap gambar. Informasi tersebut meliputi waktu dan tanggal pemotretan (*timestamp*), detail manufaktur perangkat, resolusi piksel, parameter optik, hingga tag *Global Positioning System* (GPS) yang memuat nilai matematis koordinat lintang (*latitude*) dan bujur (*longitude*) lokasi pengambilan gambar [2].

Dalam operasional pemantauan infrastruktur jaringan telekomunikasi, mekanisme pelaporan koordinat geografis yang diinput secara manual sangat rentan terhadap manipulasi kelalaian, ketidakakuratan titik aset, hingga indikasi pemalsuan data lapangan. Sebagai langkah preventif, perancangan aplikasi *Dashboard Evidence* mengadopsi mekanisme ekstraksi koordinat spasial berbasis pembacaan bawaan (native) berkas foto. Ketika petugas teknis mengunggah foto *evidence*, antarmuka sistem akan secara algoritmik mengekstraksi (*parse*) blok data tag EXIF GPS yang tersembunyi di dalam struktur file citra tersebut untuk mendapatkan koordinat spasial aslinya [3]. Ekstraksi metadata ini tidak hanya berfungsi sebagai mekanisme penandaan geolokasi (*geotagging*) yang mengotomatisasi pengisian data koordinat, tetapi lebih jauh lagi menjamin integritas validitas ruang spasial aset, memastikan bahwa bukti fisik tersebut mutlak diambil secara langsung di lokasi proyek tanpa rekayasa geografis.

#### 3.4.2 KML (Keyhole Markup Language)

*Keyhole Markup Language* (KML) merupakan sebuah format data standar berbasis *Extensible Markup Language* (XML) yang dirancang khusus untuk menyimpan, memodelkan, dan merepresentasikan informasi geospasial geografis. Dikembangkan pada awalnya oleh Keyhole, Inc., yang kemudian diakuisisi oleh Google, KML secara fundamental digunakan sebagai bahasa utama untuk menampilkan data pada peramban spasial dua maupun tiga dimensi, seperti Google Earth dan Google Maps. Mengingat utilitasnya yang krusial, pada tahun 2008 format ini resmi diadopsi sebagai standar pemetaan internasional oleh konsorsium geospasial terbuka, *Open Geospatial Consortium* (OGC) [1]. Melalui sintaks berbasis *tag* yang terstruktur, format KML memiliki fleksibilitas tinggi dalam memvisualisasikan berbagai bentuk topologi entitas, mulai dari penanda titik lokasi (*placemarks*), lintasan rute garis (*paths*), pemetaan poligon batas wilayah, hingga atribut metadata spasial tambahan [2].

Dalam arsitektur sistem *Dashboard Evidence*, file berformat KML diimplementasikan sebagai parameter utama untuk melakukan validasi tata letak infrastruktur. Desain perencanaan rute proyek pembangunan atau pemeliharaan tiang utilitas jaringan diekspor dan disimpan menggunakan format file `.kml`, yang selanjutnya dirender sebagai lapisan rute linier (*spatial overlay*) di atas komponen peta digital interaktif web. Ketika titik koordinat GPS berhasil diekstraksi secara otomatis dari foto *evidence* (melalui metadata EXIF), titik geolokasi aktual tersebut akan divisualisasikan dan ditumpangkan (*superimposed*) di atas peta yang sama. Mekanisme ini secara visual akan mencocokkan apakah letak tiang yang difoto berada selaras atau melenceng dari rute lintasan (KML) yang telah diplot dalam desain proyek [3]. Integrasi presisi antara data spasial EXIF dengan peta KML ini memberikan instrumen verifikasi mutlak bagi administrator PT Telkom Indonesia (Persero) Tbk Regional III untuk memastikan bahwa fisik pengerjaan infrastruktur berlokasi tepat pada rancangan geografis yang disepakati.

#### 3.4.3 Algoritma Haversine

Dalam ilmu navigasi dan pemetaan geospasial, penghitungan jarak garis lurus antara dua titik koordinat di permukaan bumi tidak dapat dilakukan menggunakan rumus jarak Euclidean biasa (Teorema Pythagoras). Hal ini disebabkan karena bumi tidak berbentuk datar, melainkan memiliki kelengkungan berupa bentuk bola (sferis). Untuk mengatasi masalah kelengkungan geografis tersebut, metode matematis yang paling akurat dan umum digunakan adalah Algoritma *Haversine* [1]. Rumus Haversine merupakan persamaan trigonometri navigasi sferis yang menentukan jarak busur terpendek (*great-circle distance*) antara dua titik berdasarkan nilai bujur (*longitude*) dan lintang (*latitude*), dengan memperhitungkan radius kelengkungan rata-rata bumi [2].

Pada implementasi aplikasi *Dashboard Evidence*, Algoritma Haversine berperan krusial dalam fitur fungsi validasi spasial (geofencing) otomatis. Algoritma ini disematkan di dalam layanan logika sistem (*exifService.js*) untuk mengalkulasi jarak nyata (dalam satuan meter atau kilometer) antara dua parameter spasial: yaitu titik koordinat aktual lapangan yang diekstraksi dari metadata EXIF foto *evidence*, dan titik referensi koordinat infrastruktur yang didefinisikan di dalam data KML [3]. Jika jarak hasil kalkulasi Haversine melampaui ambang batas deviasi (*radius threshold*) yang ditoleransi, sistem akan memunculkan peringatan ketidaksesuaian lokasi. Penggunaan matematis ini menjamin akurasi tinggi dalam memastikan bahwa tiang telekomunikasi yang dilaporkan oleh pekerja benar-benar terpasang di lokasi proyek yang ditargetkan tanpa selisih jarak yang mencurigakan.

### 3.5 Pemodelan Sistem

#### 3.5.1 Activity Diagram

*Activity Diagram* (Diagram Aktivitas) merupakan salah satu komponen instrumen pemodelan visual berbasis *Unified Modeling Language* (UML) yang difokuskan untuk menggambarkan aspek dinamis dari sebuah sistem perangkat lunak. Secara fundamental, diagram ini memiliki fungsi yang menyerupai diagram alir (*flowchart*) tingkat lanjut, yakni merepresentasikan urutan alur kerja logika (*workflow*) atau aliran eksekusi kontrol dari satu entitas aktivitas ke aktivitas lainnya secara kronologis, baik secara berurutan (*sequential*) maupun paralel [1]. Komponen struktural pada diagram ini umumnya mencakup penanda simpul awal (*initial node*), daftar tindakan (*activities/action states*), percabangan kondisi atau logika keputusan (*decision nodes*), hingga simpul akhir (*final node*) yang menandakan terminasi sebuah proses sistem operasi [2].

Dalam konteks perancangan arsitektur *Dashboard Evidence*, pembuatan *Activity Diagram* digunakan sebagai landasan *blueprint* rekayasa perangkat lunak untuk mendeskripsikan bagaimana interaksi fungsional antara pengguna (*validator*) dan sistem *backend* dieksekusi secara nyata. Diagram ini secara sistematis memetakan langkah demi langkah alur logika validasi aplikasi: dimulai dari fase pengguna mengunggah citra foto lapangan, yang kemudian memicu sistem untuk secara internal mengeksekusi algoritma pendeteksi objek YOLOv8. Apabila model berhasil mendeteksi objek fisik tiang, alur akan diteruskan pada proses ekstraksi koordinat metadata EXIF, lalu diakhiri dengan komputasi kalkulasi jarak (Algoritma Haversine) terhadap titik rute geospasial proyek (KML) [3]. Melalui pemodelan UML ini, kelayakan struktur alur validasi *evidence* dapat dipastikan beroperasi secara runtut, logis, serta terbebas dari kebuntuan sistem (*deadlock*).
